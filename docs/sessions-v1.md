# Study sessions, review observations and persistence v1

Import createStudySession from ./session. The session composes the actual Core persistent runtime with the pure study ports. It preserves the Protocol EngineSession methods and adds Core lifecycle/state subscriptions, getProgress and standard event subscriptions. Start moves created to active. Completion requires every card to be reviewed or explicitly skipped unless allowPartialCompletion is enabled. An empty deck completes immediately after start.

Self-ratings remain subjective confidence with correctness=null. acknowledge records an optional unrated review after reveal (or without reveal in exam-like mode); its confidence is null, and it is never interpreted as incorrect or correct. Each card has at most one rating or acknowledgment per session. Guided/exam forward movement accepts either kind of review. Protocol completion is unevaluable/unassessed, with no score.

Session state uses sessionStateVersion 1.0.0 around unchanged StudyState 1.0.0 plus ordered reviewHistory and a sessionPolicyKey. Core serializes this through its runtimeVersion 1.0.0 Snapshot state. Ordering, seed-selected permutation, current position, revealed face, skipped cards, subjective reviews and unrated history survive JSON round trips. No deck face text, hints, tags, metadata, credential, callback or driver handle is copied into the snapshot.

Restore uses Core's exact activity/schema/engine/state/session/attempt/content digest checks and domain allowlists. Stored order must equal the seeded/guided order captured for this source deck and policy. Review timestamps, ID uniqueness, confidence/rating relationships and history/study consistency are checked before commit. A source deck change, even with retained IDs, changes the digest and rejects restore; the host starts a new session or explicitly approves an external migration. No implicit permutation regeneration, card matching or loss of history occurs. Core rotates generation and emits activity.resumed on restore; the revealed face remains unchanged.

Local events keep the standard Events v1 envelope, IDs, activity/session/attempt/source, sequence, timestamp and causation. Start/completion use activity.started/completed. Card exposures and review outcomes are declared optional extensions under interactive-project.flashcards/observation on standard events. This preserves the existing closed type catalog and allows old consumers to ignore/preserve the extension. observationVersion 1.0.0 is a Flashcards-owned schema; exposure contains only cardId/face, and review contains only cardId plus optional normalized self-report/unrated outcome. No hidden face text, hint, response transcript, tag or metadata enters an event.

The outward observation is prepared/validated and admission-budgeted inside Core's event gate before commit, then delivered after Core state notifications. Source sequence and event identity are preserved through the extension facade. Rejected actions do not publish observations. Retained outbox admission failure blocks future transitions until flushEvents recovers; no durable telemetry queue or remote exactly-once guarantee is implied.

Telemetry is disabled by default and requires an explicitly provided host sink. Local state/event subscriptions remain available when telemetry is disabled. Enabled telemetry excludes card IDs and the entire observation by default. includeCardIds permits pseudonymous card/face metadata; includeRatings additionally permits subjective rating/confidence. When ratings are filtered, outcome is omitted rather than falsely declaring an unrated review. Activity/session/source correlation remains in standard envelopes; the host owns authorization, retention and further pseudonymization. Sink exceptions/rejected promises cannot alter domain state. No network transport is implicit.

Tests cover complete/empty sessions, interrupted revealed review, seeded cross-host persistence, policy/source changes, corrupt order, unchanged state/generation after rejection, subjective versus unrated outcomes, event sequences/counts, disabled telemetry, metadata/back filtering and outcome schema validation.
